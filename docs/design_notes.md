# 설계 결정 정리

이 프로젝트의 설계 결정과 그 근거를 질문·답 형태로 정리했습니다.
숫자는 모두 `results/tables/`의 결과 파일에서 가져왔습니다.

## 요약

> OMOP CDM 형식의 합성 의료 데이터에서 SQL로 NSAID 신규 사용자 코호트를 만들었습니다.
> 골관절염 환자 중 celecoxib 또는 diclofenac을 처음 처방받은 2,694명에서 선정기준을 적용해 2,630명을 확정하고,
> 처방 후 1년 내 위장관 출혈 발생을 비교했습니다.
> 보정 전에는 celecoxib 군의 출혈이 더 많았는데(19.7% 대 14.9%), 기저 특성을 보니 celecoxib 군에 소화성 궤양 과거력이 두 배 이상 많았습니다.
> 궤양 과거력으로 층화하자 과거력이 없는 층에서는 방향이 반대로 나왔습니다.
> 코호트를 뽑는 것만큼, 뽑은 집단이 비교 가능한지 확인하는 과정이 중요하다는 것을 배웠습니다.

## 용어 한 줄 정리

| 용어 | 뜻 |
|---|---|
| OMOP CDM | 병원마다 다른 의료 데이터를 같은 테이블 구조와 표준 용어로 맞춘 공통 데이터 모델 |
| OHDSI | OMOP CDM과 분석 도구를 만드는 국제 연구 커뮤니티 |
| concept_id | 모든 진단·약물·검사를 나타내는 표준 숫자 코드. `concept` 테이블이 사전 역할 |
| 표준 용어 | 진단 SNOMED CT, 약물 RxNorm, 검사 LOINC |
| 관찰기간 | 환자의 기록이 빠짐없이 수집된다고 볼 수 있는 기간. 분석의 분모 |
| 지표일 (index date) | 코호트 진입일. 이 프로젝트에서는 첫 처방일 |
| 신규 사용자 설계 | 약을 처음 시작한 사람만 포함하는 설계 |
| washout / lookback | 지표일 이전에 약물 이력이 없음을 확인하는 기간 (여기서는 365일) |
| 중도절단 (censoring) | 사건이 생기기 전에 추적이 끝난 경우 |
| 인년 (person-year) | 환자들의 추적 기간을 모두 더한 값. 추적 기간이 다른 집단을 비교할 때의 분모 |
| SMD | 표준화 평균차. 두 집단 특성의 차이를 표준편차 단위로 표현. 0.1 초과면 불균형 |
| 교란 (confounding) | 노출과 결과 양쪽에 영향을 주는 제3의 요인 때문에 관계가 왜곡되는 것 |
| RWD / RWE | 진료 과정에서 쌓인 실제 데이터 / 그것을 분석해 얻은 근거 |
| ETL | 원본 EMR을 CDM 형식으로 변환·적재하는 과정 |
| ACHILLES | CDM 데이터베이스 전체를 자동으로 요약하는 OHDSI 도구 |

## 설계 결정 Q&A

### Q. 왜 신규 사용자만 포함했나요?
이미 오래 복용 중인 사람은 초기에 부작용을 겪은 사람이 빠져나간 뒤 남은 집단이라, 포함하면 약이 실제보다 안전해 보입니다.
또 기존 복용자는 "언제부터 추적을 시작할지"가 모호하고, 기저 특성이 이미 약의 영향을 받은 상태일 수 있습니다.
구현은 `ROW_NUMBER() OVER (PARTITION BY person_id ORDER BY 처방일)`로 환자별 첫 처방만 남겼습니다 (`c01`).

### Q. `MIN()`으로도 첫 처방일을 구할 수 있는데 왜 `ROW_NUMBER`를 썼나요?
날짜만 필요하면 `MIN()`으로 충분합니다. 여기서는 "그 첫 처방이 어떤 성분이었는지"를 같은 행에서 가져와야 해서 행 자체를 골라야 했습니다.
같은 날 두 약이 있을 때 결과가 실행마다 달라지지 않도록 2차 정렬 키도 넣었습니다.

### Q. 관찰기간 조건은 왜 필요한가요?
기록이 없다는 것이 "사건이 없었다"는 뜻인지 "그 기간에 이 병원에 다니지 않았다"는 뜻인지 구분하기 위해서입니다.
지표일 이전 365일이 관찰기간에 포함되어야 그 기간에 처방 이력이 없었다는 것을 믿을 수 있습니다.
이 데이터에서는 지표일이 관찰기간 밖인 환자가 64명 있어 제외했습니다.

### Q. 약물을 어떻게 찾았나요? 약 이름으로 검색했나요?
`drug_exposure`에는 약이 "Ibuprofen 200 MG Oral Tablet"처럼 제품 단위로 들어 있습니다.
이름을 `LIKE`로 검색하면 누락이나 오탐이 생기므로, `concept_ancestor` 테이블에서 성분 concept의 하위 제품을 모두 가져왔습니다.
성분 concept ID 하나만 알면 용량과 제형이 다른 제품이 전부 잡힙니다 (`b04`, `c01`).

### Q. 기저 특성을 만들 때 가장 주의한 점은?
지표일 이전 정보만 쓰는 것입니다. 지표일 이후 정보가 섞이면 미래 정보로 과거를 설명하게 됩니다. 머신러닝의 데이터 누수와 같은 문제입니다.
그래서 `c04`의 모든 조인 조건에 `사건일 < cohort_start_date`를 넣었습니다.
만성 질환은 전체 과거를, 병용 약물과 입원은 최근 365일을 봤습니다.

### Q. 보정 전 결과와 층화 결과가 왜 달랐나요?
celecoxib 군에 소화성 궤양 과거력이 있는 환자가 36.6%, diclofenac 군은 15.9%였습니다.
궤양 과거력이 있으면 출혈 위험이 원래 높으므로(과거력 있음 33.7% 대 없음 11.6%), 약의 효과와 환자 구성의 차이가 섞여 있었습니다.
층화하니 과거력 없는 층은 9.8% 대 14.5%, 있는 층은 36.9% 대 17.4%로 층마다 방향이 달랐습니다.
다만 합성 데이터이고 변수 하나로만 층화했기 때문에 이 숫자 자체를 약의 효과로 해석하지는 않습니다.

### Q. 왜 p-value 대신 SMD를 봤나요?
p-value는 표본이 크면 의미 없는 작은 차이에도 유의하게 나옵니다.
균형을 볼 때 알고 싶은 것은 "차이가 통계적으로 유의한가"가 아니라 "차이가 얼마나 큰가"이므로 표본 크기에 영향받지 않는 SMD를 씁니다.

### Q. 누적 발생률과 인년당 발생률을 둘 다 계산한 이유는?
누적 발생률(사건 수 ÷ 환자 수)은 이해하기 쉽지만 모든 환자를 같은 기간 추적했다고 가정합니다.
실제로는 관찰기간이 일찍 끝나는 환자가 있어서, 추적 기간의 합을 분모로 쓰는 인년당 발생률을 함께 냈습니다.
Kaplan-Meier도 같은 이유로 썼고, 원리를 설명할 수 있도록 라이브러리 없이 구현했습니다.

### Q. SQL 결과가 맞는지 어떻게 확인했나요?
네 가지 방법을 썼습니다.
1. 처방을 연속 복용 기간으로 묶는 로직(`p04`)을 직접 짜고, CDM에 미리 계산되어 있는 `drug_era` 테이블과 비교했습니다. 4,304건으로 일치했습니다.
2. 제외 조건을 `NOT EXISTS`, `LEFT JOIN`, `EXCEPT` 세 방식으로 짜서 같은 숫자가 나오는지 봤습니다 (`p06`).
3. ACHILLES가 계산한 약물별 환자 수가 제 코호트 인원과 일치하는지 확인했습니다.
4. 실행 스크립트에 "환자당 1행인가", "코호트에 중복 환자가 없는가"를 `assert`로 넣었습니다.

### Q. 조인하다가 숫자가 틀린 적이 있나요? 어떻게 방지하나요?
진단과 처방처럼 환자당 여러 행인 테이블 두 개를 한꺼번에 조인하면 행이 곱으로 늘어나 건수가 부풀려집니다.
오류 없이 그럴듯한 숫자가 나오기 때문에 위험합니다.
테이블별로 먼저 환자당 1행으로 집계한 다음 조인하고(`i02`), 결과 행 수가 환자 수와 같은지 확인합니다.
존재 여부만 필요할 때는 조인 대신 `EXISTS`를 씁니다.

### Q. 데이터에서 발견한 문제가 있었나요?
- `observation_period`에 `person`에 없는 환자 행이 2,649개 있어서, 그대로 세면 환자 수가 두 배로 나옵니다.
- 처방의 99.7%가 방문 기록과 연결되지 않아 방문 단위 분석을 할 수 없었습니다.
- 검사 결과 수치가 전부 비어 있었습니다.
- 대상 약물의 `days_supply`가 모두 0이라 복용 기간을 알 수 없었습니다. 그래서 복용 중인 기간만 추적하는 대신, 시작한 약 기준으로 1년을 추적하는 방식을 택했습니다.

### Q. ACHILLES는 무엇이고 왜 돌렸나요?
CDM 데이터베이스의 인구 구성, 진단·약물 빈도, 관찰기간 분포 등을 표준화된 분석 수백 개로 자동 요약하는 도구입니다.
병원이 CDM을 구축한 뒤 변환이 제대로 됐는지 확인할 때 씁니다.
제가 손으로 짠 요약 쿼리의 숫자를 교차 확인하는 용도로도 썼습니다.
DuckDB에서는 결과 적재 단계에서 컬럼 대소문자 오류가 나서, ACHILLES만 SQLite 판에서 실행했습니다.

### Q. MIMIC 데이터는 왜 추가했나요?
CDM의 목적이 "같은 분석 코드를 여러 기관에서 돌리는 것"이라 실제로 그렇게 되는지 확인하고 싶었습니다.
같은 SQL 파일이 수정 없이 실행됐습니다.
동시에 한계도 확인했습니다. MIMIC demo 공개본에는 표준 용어 사전이 빠져 있어 concept 이름 조인이 되지 않았고,
중환자실 데이터라 관찰기간 중앙값이 65일로 짧아서 Eunomia에서 한 1년 추적 코호트 설계를 그대로 적용할 수 없었습니다.

### Q. 실제 병원 데이터였다면 무엇이 달라졌을까요?
- 선정기준마다 탈락자가 많이 생기고, 그 숫자를 근거로 기준을 조정해야 했을 것입니다.
- 진단 하나가 아니라 하위 개념을 포함한 개념 집합을 임상가와 함께 정의해야 합니다.
- 환자당 관찰기간이 여러 개일 수 있고, 결측과 입력 오류를 처리해야 합니다.
- 수백만 명 규모에서는 쿼리 성능을 고려해야 합니다.
- 교란 보정을 위해 성향점수 매칭 같은 방법이 필요합니다.

### Q. 이 프로젝트의 한계는?
합성 데이터라 임상적 결론을 낼 수 없고, 교란 보정은 변수 하나로 층화한 수준입니다.
실제 복용 기간을 알 수 없어 약 중단이나 변경을 반영하지 못했습니다.
다음 단계로는 성향점수 매칭과 Cox 모형, 그리고 같은 코호트를 OHDSI ATLAS로 정의해 제 SQL 결과와 비교하는 것을 생각하고 있습니다.

## 핵심 SQL 3개

이 레포의 접근을 가장 잘 보여 주는 파일은 다음 세 개입니다.

1. `sql/03_cohort/c01_cohort_candidates.sql` — CTE, `concept_ancestor` 조인, `ROW_NUMBER`, `EXISTS` 상관 서브쿼리가 한 쿼리에 들어 있고 선정기준과 1:1로 대응됩니다.
2. `sql/04_patterns/p04_gaps_and_islands_drug_era.sql` — 윈도우 함수 응용(누적 최댓값 → 구간 시작 표시 → 누적합)이고 정답 테이블과 일치함을 보여 줄 수 있습니다.
3. `sql/02_intermediate/i02_patient_summary_avoid_fanout.sql` — 조인으로 행이 늘어나는 문제와 해결 방법을 보여 줍니다.
